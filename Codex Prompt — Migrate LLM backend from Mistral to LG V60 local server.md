# IMPORTANT: deterministic calculations are authoritative

This section is critical.

The local 2B model has already demonstrated that it can misinterpret numeric telemetry even when the arithmetic is simple.

Example failure:

Tool returned:

{
  "fuel_liters": 12.4,
  "average_liters_per_lap": 2.1,
  "race_laps_remaining": 5,
  "estimated_laps_remaining": 5.9,
  "estimated_margin_laps": 0.9
}

The model incorrectly interpreted positive 0.9 margin as a fuel deficit.

Therefore:

THE LLM MUST NOT PERFORM DETERMINISTIC RACE CALCULATIONS.

THE LLM MUST NOT REINTERPRET AUTHORITATIVE STATUS FIELDS.

All arithmetic and deterministic conclusions must be calculated in C++ before being sent to the LLM.

The LLM's role should primarily be:

structured facts
    ->
short natural-language response

NOT:

raw numbers
    ->
reasoning
    ->
math
    ->
conclusion

---

# Tool result design rule

Every tool that can produce a deterministic conclusion must include an explicit semantic conclusion.

Do not rely on the model to infer the conclusion from raw numbers.

Example BAD:

{
  "fuel_liters": 12.4,
  "avg_l_per_lap": 2.1,
  "laps_remaining": 5,
  "estimated_laps_remaining": 5.9,
  "margin_laps": 0.9
}

Example GOOD:

{
  "enough_fuel": true,
  "fuel_status": "surplus",
  "spare_laps": 0.9,
  "fuel_liters": 12.4,
  "avg_l_per_lap": 2.1,
  "laps_remaining": 5
}

The conclusion fields must be generated by C++.

---

# Fuel calculation rules

Implement fuel calculations deterministically in C++.

Example:

estimated_laps_available =
    current_fuel / average_fuel_per_lap

fuel_margin_laps =
    estimated_laps_available - race_laps_remaining

enough_fuel =
    estimated_laps_available >= race_laps_remaining

Return authoritative semantics such as:

{
  "available": true,
  "enough_fuel": true,
  "fuel_status": "surplus",
  "spare_laps": 0.9,
  "estimated_laps_available": 5.9,
  "race_laps_remaining": 5
}

If deficit:

{
  "available": true,
  "enough_fuel": false,
  "fuel_status": "deficit",
  "missing_laps": 0.7
}

Never use a single ambiguous signed field if a semantic field can be added.

Prefer:

spare_laps

and:

missing_laps

instead of relying only on:

margin_laps = +/- value

# System prompt changes

Update the race engineer system prompt.

It must include concepts similar to:

"You are a concise race engineer assisting a driver in real time.

Keep responses very short.

Prefer one short sentence.

Never invent telemetry.

Use telemetry tools whenever live race information is required.

Treat deterministic fields returned by tools as authoritative.

Do not recalculate arithmetic that has already been calculated by the application.

Do not reinterpret status fields such as enough_fuel, fuel_status, trend, critical, overheating, or available.

If enough_fuel is true, never describe the car as short on fuel.

If fuel_status is surplus, never describe it as a deficit.

If fuel_status is deficit, never describe it as spare fuel.

If a field is unavailable, say the data is unavailable.

Do not explain reasoning unless explicitly requested."

Keep the actual production system prompt compact to reduce prompt-processing latency.

# Tool descriptions must be explicit

The model is small.

Tool schemas and descriptions must avoid ambiguity.

Example:

get_fuel_status description:

"Returns authoritative pre-calculated fuel status.

Do not recalculate fuel requirements.

`enough_fuel=true` means there is enough fuel to finish.

`fuel_status=surplus` means spare fuel remains.

`fuel_status=deficit` means more fuel is required.

`spare_laps` is always non-negative and only appears when fuel_status is surplus.

`missing_laps` is always non-negative and only appears when fuel_status is deficit."

Use similarly explicit descriptions for other tools.

# Error handling for model mistakes

Implement basic post-validation for high-value deterministic answers.

For example, after get_fuel_status():

If:

enough_fuel == true

and the final model response contains an obviously contradictory structured intent if detectable,

do not trust model reasoning.

Prefer one of these approaches:

1. regenerate once using a stricter instruction, or
2. bypass the LLM and produce a deterministic fallback phrase.

Preferred fallback examples:

If:

enough_fuel = true
spare_laps = 0.9

fallback:

"Fuel good. 0.9 laps spare."

If:

enough_fuel = false
missing_laps = 0.7

fallback:

"Fuel short by about 0.7 laps."

For critical deterministic information, reliability is more important than natural phrasing.
